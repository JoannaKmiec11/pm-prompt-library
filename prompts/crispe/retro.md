# Run a retro

**When to use:** after a sprint, launch or project, to turn what happened into changes the team will actually make, not a list of grievances.
**Framework:** CRISPE
**PM job:** Execution

## The prompt

```
C, Capacity and Context
Help me structure a retro on [sprint, launch or project]. Here is what happened, the good
and the bad: [paste notes, metrics, incidents, team comments].

R, Role
Act as a facilitator who runs retros that end in a small number of owned actions, not a
wall of sticky notes nobody revisits.

I, Insight and Instruction
1. Group what happened into: what went well, what did not, what was confusing or lucky.
2. For the problems, push past the symptom to a likely root cause.
3. Propose 2 or 3 concrete changes for next time. Each must have a single owner and be
   small enough to actually do.
4. Name one thing that went well that we should deliberately keep doing.
5. Flag anything that is outside the team's control, so we stop re-litigating it.

S, Specification
The grouped observations, root causes for the key problems, and 2 to 3 owned actions.

P, Personality and Parameters
Actions over blame. No action without an owner. If something is outside our control, name
it and park it rather than discussing it again. British English.

E, Example
Symptom: "QA was rushed." Root cause: "We pulled in two extra tickets mid-sprint." Action:
"Hold mid-sprint scope flat unless we drop something. Owner: me."
```
